# DuckDB 1.5 + Sirius GPU加速

> **一句话摘要**：DuckDB 1.5.1发布ExtensionKit（C#扩展）+存储格式升级+Parquet Bloom Filter（10-100x）；Sirius GPU扩展利用NVIDIA cuDF实现ClickBench 7.2x性价比提升。

> **来源**：chenxutan.com（程序员茄子），2026-04-08

## 核心要点

1. **DuckDB 1.5 ExtensionKit**：用C#编写扩展，降低开发门槛，从"工具"→"平台"
2. **Parquet Bloom Filter**：百万行日志表查询性能提升10-100倍
3. **Sirius GPU ClickBench**：GH200上性价比提升7.2x（vs纯CPU DuckDB），复杂查询优势显著
4. **零拷贝架构**：Sirius ← Arrow ← cuDF，数据在格式间零开销转换
5. **JIT正则突破**：Q28正则查询JIT编译比朴素GPU实现快13x，寄存器占用从32%→85%

## 详细数据

| 系统 | ClickBench相对时间 | 性价比 |
|------|:---:|:---:|
| Sirius (GPU) | 1.0 | 7.2x |
| Umbra | 1.3 | - |
| DuckDB (CPU) | 2.1 | - |
| ClickHouse | 2.4 | - |

## 适用场景

- ✅ 大规模聚合（GROUP BY/COUNT/SUM）、多表JOIN、复杂表达式
- ✅ 重复查询（GPU缓存热数据）
- ❌ 小数据集(<100MB)、纯I/O瓶颈、字符串密集查询

## 结论

DuckDB 1.5 这一轮更新有两条并行主线：一条是把自己从「嵌入式查询工具」推向「平台」（ExtensionKit 支持用 C# 写扩展、存储格式升级），另一条是用 Sirius 扩展验证 GPU 加速的性价比边界——在 GH200 上 ClickBench 性价比达纯 CPU DuckDB 的 7.2 倍，且通过 Arrow ← cuDF 实现零拷贝。但适用场景的边界写得很清楚：GPU 只在「大规模聚合 + 多表 JOIN + 复杂表达式 + 重复查询」时占优，小数据集（<100MB）、纯 I/O 瓶颈、字符串密集查询反而吃亏。Parquet Bloom Filter 带来的 10–100 倍提升则是普适性收益，百万行日志表场景即可兑现。
