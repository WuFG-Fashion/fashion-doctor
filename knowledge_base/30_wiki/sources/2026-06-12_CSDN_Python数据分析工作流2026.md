# Python 数据分析与可视化完整工作流 2026

> **一句话摘要**：CRISP-DM 七步工作流 + Pandas/Polars/DuckDB 三件套选型矩阵 + EDA 三大分析 + 可视化全家桶，针对服装零售场景映射每个步骤。

> **来源**：CSDN（https://blog.csdn.net/likuoelie/article/details/161007752）
> **最后更新**：2026-06-12

## 核心要点

1. **CRISP-DM 七步**：定义问题→数据获取→清洗→EDA→特征工程→建模→沟通，每步映射服装零售场景
2. **三件套选型**：Pandas(10万行以下)/Polars(百万-千万行)/DuckDB(亿级)，按数据规模选择
3. **EDA 三类**：单变量(直方图/箱线图)+多变量(热力图/散点图)+时间序列(趋势/季节性)
4. **可视化栈**：Matplotlib→Seaborn→Plotly Express(交互)→Altair+Great Tables→ydata-profiling(自动化)
5. **服装零售图表推荐**：Treemap(品类占比)/Sankey(转化路径)/热力图(库存周转)/散点图(价格-销量)

## 结论

本页是**方法论完整度最高的一页**：CRISP-DM 七步工作流 + 三件套选型矩阵（Pandas / Polars / DuckDB 按数据规模分层）+ EDA 三类分析 + 可视化工具栈，**且每一条都映射到了服装零售场景**。`confidence: 第三方数据`（CSDN 博主整理）。

**本页最实用的是「按数据规模选工具」的矩阵：<10 万行用 Pandas、百万-千万行用 Polars、亿级用 DuckDB。** **这个分层对服装零售有直接意义，因为服装数据天然分三层颗粒度**：单店日销（小规模）、全渠道月销与 RFM（中等规模）、供应链与历史全量（大规模）。**多数服装企业的数据团队用一把锤子打所有钉子（全部用 Pandas 或全部上大数据平台），本页给出的分层标准正好对症。**

**七步工作流中，「数据清洗」这一步的零售示例最有价值：退货负值 / 缺失尺码 / 重复订单**。**这三类恰好是服装销售数据最典型的三个脏数据来源**，且都会直接影响分析结论：
- **退货负值**：若不剔除或未对冲，会低估真实销量、扭曲售罄率；
- **缺失尺码**：会导致尺码结构分析失真（齐码率、断码率计算错误）；
- **重复订单**：会虚增销售额与会员消费频次。

**这三条建议固化为服装数据分析的标准数据质量检查清单**，比泛泛的「数据清洗」有用得多。

**可视化推荐中，「Treemap（品类占比）/ Sankey（转化路径）/ 热力图（库存周转）/ 散点图（价格-销量）」的对应关系便于落地**。**其中「散点图（价格-销量）」对服装定价与选品有直接分析价值**——它能一眼看出「高价高销」「低价低销」「高价低销」（应淘汰）等象限分布，**是商品结构诊断的高效工具**。

**三件套中 DuckDB 的定位值得注意：「亿级行 + 复杂 SQL」** —— **它把 OLAP 能力带入了单机 Python 环境，对本库这类自建轻量栈（SQLite + Python）是潜在的升级路径**（SQLite 在复杂聚合查询上的性能瓶颈是可预见的）。**本页提到 DuckDB，库内也已有 [[duckdb_olap_engine_2026]] 专页，两页应交叉引用。**

**学习路线部分（1-2 周 NumPy+Pandas → 2-4 周 EDA+Plotly → 持续 Polars+Streamlit）对个人能力建设有参考性**，但**对已经具备自建栈的团队价值有限**。

## 前沿

- **「三类脏数据」建议固化为标准检查清单（最高优先级）**：退货负值 / 缺失尺码 / 重复订单**恰好对应服装销售数据的三个典型污染源，且各自会扭曲不同指标**（售罄率 / 齐码率 / 会员频次）。建议写入数据质量相关概念页作为固化检查项。
- **规模分层阈值需结合硬件校准**：<10 万行 / 百万-千万行 / 亿级 的分层是通用参考，**实际拐点取决于机器配置与本库的具体查询模式**，建议在概念页标注「需按自身环境实测」。
- **DuckDB 与本库栈的适配建议评估**：本库现为 SQLite，**DuckDB 在复杂聚合上的优势可预见**，但迁移成本（SQL 方言差异、生态兼容）需评估。建议与 [[duckdb_olap_engine_2026]] 交叉引用并单列一次可行性评估。
