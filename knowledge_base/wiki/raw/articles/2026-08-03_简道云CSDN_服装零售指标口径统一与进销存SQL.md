## 一、核心命题：一个 SKU、一套口径、一个真相

服装行业常见问题是多个系统并行（ERP、电商、WMS、POS、财务），导致：
- 库存口径不一致
- 入库/出库时点不统一
- 在途与在库分离

## 二、核心指标口径对照表

| 指标 | 定义 | 公式 | 注意事项 |
|------|------|------|---------|
| 期末库存 | 某时点商品在库数量 | 期初 + 入库累加 - 出库累加 | 对齐时区，处理取消/冲销 |
| 库存周转天数 | 库存被售出的平均时间 | 期末库存 / 日均销量 | 异常销量剔除 |
| 库存周转率 | 资金使用效率 | 销售成本 ÷ 平均库存成本 | 也有"周期销售额/周期平均库存额"口径 |
| 毛利率 | 销售盈利水平 | (含税销售额 - 含税成本) / 含税销售额 | 折扣与返利口径一致 |
| **售罄率** | 商品力与促销有效性 | **销量 / (期初库存 + 期间入库 - 退货)** | 分母是总到货量还是总采购量需明确 |
| 动销率 | 识别僵尸 SKU | 有销售记录 SKU / 总 SKU | 日/周监控 |
| **断码率** | 尺码齐全度 | 有销售但缺某尺码的 SKU 数 / 在售 SKU 数 | 缺 1 码算不算需定义 |
| 滞销 SKU | 长时间未售出 | 最近 N 天销量=0 且库存>阈值 | 季节性与促销影响 |

## 三、服装行业目标阈值参考（ERP 选型视角）

| 指标 | 目标阈值 |
|------|---------|
| 库存周转率 | 年化 **6~10**（快时尚可 >12） |
| 库存周转天数 | **36~60 天**（品类差异化） |
| 售罄率 | **新款首月 >60%，季度 >80%** |
| 断码率 | 越低越好（用于补货优先级判断） |
| 预测与备货质量 | 准确率 >85% |

> 口径提示：上述为 ERP 厂商给出的经营目标值（快反/DTC 语境），与上市公司年报口径、季末大盘售罄率口径不同，横向比较前需先对齐分母与时间窗。

## 四、常用算法

- **需求预测**：加权移动平均（近期权重更高）+ 节假日/促销活动系数修正；新品采用同款型/同风格类比曲线
- **ABC-XYZ 分类**：ABC 按销售贡献，XYZ 按需求稳定性（波动系数）。A/X 类高服务水准 + 频繁补货；C/Z 类低安全库存 + 快清理
- **动态安全库存**：`SafetyStock = Z × σd × √L`，Z 为服务水准系数（95% ≈ 1.65），σd 为需求标准差，L 为供货周期（周）
- **订货点 ROP**：`ROP = 日均需求 × 供货周期天数 + 安全库存`；门店级 ROP 需结合最小展示量（Facing）与尺码曲线

## 五、SQL 查询方法论

### 5.1 六种核心写法（覆盖常见业务问题 85%）

| 写法 | 用途 |
|------|------|
| `LEFT JOIN + COALESCE` | 容错合并 |
| 窗口函数 `SUM(...) OVER(PARTITION BY ... ORDER BY ... ROWS UNBOUNDED PRECEDING)` | 计算时点库存 |
| CTE 分层 `WITH raw AS (...), agg AS (...), final AS (...)` | 提高可读性与复用率 |
| 分组聚合 `GROUP BY product_id, date_trunc('month', move_time)` | 形成月报口径 |
| 条件聚合 `SUM(CASE WHEN move_type='IN' THEN qty ELSE 0 END) in_qty` | 出入库拆分 |
| 物化快照 `snap_inventory_daily` | 每日库存余额写入，加速 T+0/历史查询 |

### 5.2 查询性能五策略（实测收益）

| 策略 | 做法 |
|------|------|
| 时间裁剪 | 强制 `WHERE move_time BETWEEN :start AND :end`，避免全表扫描 |
| **覆盖索引** | 查询字段尽量被索引覆盖，减少回表 |
| 冷热分层 | 近 3 个月实时算，历史走快照 |
| 并行与分区 | 月分区 + 并行聚合 |
| 预计算 | 高频指标（库存余额、周转）每日离线计算入表 |

**实测收益：IO 下降 68%，吞吐提升 2.3 倍。**

### 5.3 关键落地建议

> **将指标口径沉淀为只读视图，供报表与 BI 统一引用，避免各部门口径分裂。**

### 5.4 典型场景

- **场景 1 实时库存查询**：输入 SKU 与仓库，返回即时库存余额、批次可用量与占用量。数据源 `fact_stock_movement + dim_product + dim_warehouse`；方法为窗口累计或日快照 + 当日增量，确保秒级响应
- **场景 2 滞销预警与周转**：识别最近 N 天销量为 0 且库存大于安全库存的 SKU，计算周转天数，用于促销与清货策略

## 六、服装行业五维指标体系框架（CSDN）

| 维度 | 回答的问题 | 核心指标 | 服装特色 |
|------|-----------|---------|---------|
| 销售 | 卖得怎么样 | 销售额、达成率、同店增长、折扣率、连带率 | 连带率高 = 搭配做得好、客单价高 |
| 商品 | 卖什么好 | 爆款贡献、新品存活率、价格带 | 款/色/码三维分析 |
| **库存** | 压不压货 | 周转天数/周转率；新旧品占比、品类占比、尺码占比；**库龄分布(30/60/90/120+天)**、呆滞占比、**断码率**；红黄绿灯预警、季末库存预测、清仓进度 | **最核心是库龄和断码率**；超 90 天基本是"死库存" |
| 渠道 | 在哪卖 | 各渠道销售占比/增长率/毛利率、渠道 ROI、费用率、退货率、线上占比、同店增长、O2O 渗透 | 直营/加盟/百货/奥莱 × 天猫/京东/抖音/快手/小程序/唯品会 × 直播/私域/小红书，客群定价毛利各异，必须分渠道看 |
| 用户 | 谁在买 | 访客数、新老客占比、转化率、**复购率**、流失率、客单价、ARPU、LTV、画像 | 最核心是**复购率**和**风格偏好** |

### 6.1 落地四步法

1. **定目标找对齐** — 按企业阶段确定北极星指标
   - 品牌初创期 → 爆款贡献率
   - 快速扩张期 → 销售额或门店数
   - 精细化运营期 → 售罄率或库存周转天数
   - 用户运营期 → 复购率或 LTV
2. **盘数据清家底** — POS / 电商平台 / ERP / CRM / 商品系统 / WMS
3. **定指标建字典**
4. **分场景做应用**

### 6.2 数据打通四个关键（服装特有）

- **SPU/SKU 编码统一**：同一商品在 POS、ERP、电商平台编码一致
- **尺码/颜色标准化**：XS/S/M/L/XL 统一映射；颜色名统一（"黑色"不能有的系统叫"黑"）
- **时间口径对齐**：自然周、自然月、财周、财月要对齐
- **渠道 ID 统一**：同一门店/店铺在不同系统编码一致

### 6.3 服装指标定义的四个特殊难点

1. **售罄率**：分母是总到货量还是总采购量？时间范围 30/60/90 天？
2. **库存周转天数**：分母是销售成本还是销售收入？不同品类标准不同？
3. **断码率**：什么算"断码"？缺 1 个尺码算不算？缺 2 个呢？
4. **新品**：上市多少天内算"新品"？7 天？15 天？30 天？

**原则：一个指标，一个口径。不同品类、不同渠道、不同季节要能横向对比。**

### 6.4 分场景看板设计

| 角色 | 看板 | 内容 |
|------|------|------|
| CEO/品牌总监 | 战略驾驶舱 | 北极星指标趋势、品类结构、渠道结构、异常预警 |
| 商品企划/买手 | 商品看板 | 爆款识别 TOP50、新品动销率与存活率、品类结构、价格带、款/色/码分析 |
| 运营/销售 | 销售看板 | 销售达成、同店增长、折扣率、连带率、分渠道分区域 |
| 供应链/库存 | 库存看板 | 周转、库龄分布、售罄率追踪、补货建议、呆滞预警、清仓进度 |

## 七、异常监控清单（数据质量规则化）

- 库存负数、超安全库存、长期零销量
- 价格越界、折扣异常、毛利异常
- 在途超时、调拨滞留、退货异常
- 断码高发、尺码不均、颜色偏好异常

响应机制：**看板告警 + 企业微信推送**。

## 八、零售 BI 2026 趋势（Domo）

- 传统报表跑批：夜间任务把昨日销售拉进静态看板 → 商品经理看到某款超预期时，可能一半门店已断货
- 现代零售 BI 差异归结为三点：**Speed / Depth / Action**
- 五大核心数据源：POS、电商平台、ERP/库存、CRM/忠诚度、营销广告
- 选型需评估零售专属维度：数据连接性、延迟要求、**语义层（semantic layer）支持**、AI 能力
- 关键指标：sell-through rate、weeks-of-supply、inventory turnover、CLV，且必须有清晰定义与计算公式
- 最容易被低估的工作：跨源数据对账（teams expect a quick integration project and discover months of data cleanup instead）
