# DuckLake 1.0 数据湖格式生产就绪

> **一句话摘要**：DuckDB Labs 于 2026-04 发布 DuckLake 1.0 湖仓格式，把元数据从"文件堆"（Iceberg/Delta/Hudi 的 JSON+Avro）改存进关系型数据库目录，在小文件写入密集场景下宣称比 Iceberg 快 926× 查询 / 105× 摄入——对本项目多品牌系统的统一数据层存储选型有直接参考价值。

> **来源**：DuckDB Labs 官方发布说明（v1.5.2）+ MotherDuck 生态月报 + InfoQ/The Register 报道
> **最后更新**：2026-08-29

## 核心要点

1. **元数据进 SQL 库**：DuckLake 把 catalog/snapshot/schema/文件清单存进标准关系库（PostgreSQL / SQLite / DuckDB 自身），而非对象存储里的散落 JSON 文件。
2. **五大特性**：data inlining（≤10 行直接内联进 catalog，CHECKPOINT 落盘）、sorted tables（自动 compaction + 文件裁剪）、bucket partitioning、GEOMETRY+VARIANT 类型、Iceberg v3 兼容 deletion vectors。
3. **生产就绪**：2026-04 随 DuckDB v1.5.2 进入 production-ready，自 late-2025 起合并 108 个 PR（其中 68 个聚焦可靠性与正确性）；已是 DuckDB 下载量 Top-10 扩展，提供 DataFusion/Spark/Trino/Pandas 客户端，MotherDuck 提供托管版。
4. **对比 Iceberg/Delta/Hudi**：设置复杂度低（一行 `LOCATION`），无需 Spark/Trino/Flink 即可跑；ClickBench 冷查询中位 0.57s。

## 关键数据（厂商自测基准，待独立验证）

| 指标 | DuckLake 1.0 | 说明 |
|------|-------------|------|
| 查询速度 vs Iceberg | **926× 更快**（小文件写入密集负载） | DuckDB Labs / Pedro Holanda 对 The Register 表述 |
| 摄入速度 vs Iceberg | **105× 更快**（同上负载） | 同上 |
| COUNT(*) 元数据查询 | 8×–258× 更快 | 元数据内联，免扫 manifest |
| 部署形态 | 单文件、零依赖 | 最低 8GB 内存即可跑 |

> **置信度**：媒体估算（以上 926×/105× 为 DuckDB Labs 自测、经 The Register/InfoQ 转述，缺乏第三方独立复现，落地本项目前须以真实多品牌 POS/会员事件流做 POC 验证）

## 对本项目多品牌系统存储层的映射

```
统一数据层（原 Iceberg/Paimon 方案）
   ↓ 可替换为
DuckLake（catalog 进 PostgreSQL/SQLite + Parquet 数据）
   ├─ 小文件问题根治：POS 流水/会员行为等高频小写入内联进 catalog
   ├─ Polars / DuckDB / Spark 共享同一份 Parquet（Arrow 零拷贝）
   └─ 36 品牌明细级数据量 <10GB → 单 DuckDB + DuckLake 即可，无需重型云栈
```

- **适配点**：服装零售多品牌事件流（门店销售、会员行为、埋点）天然是"大量小写入"负载，正是 DuckLake 相对 Iceberg 宣称的优势区间。
- **风险点**：926×/105× 为极端小文件场景的厂商基准，本项目实际收益取决于写入模式；须用 `36 品牌 × 真实日增量` 做对照测试，再决定是否替换现有 Iceberg/Hudi 路线。

## 结论

1. DuckLake 1.0 把"元数据进 SQL 库"作为湖仓新范式，对**小文件写入密集**的零售多品牌事件流是结构性的存储层候选，可补强 [[multi_brand_unified_analytics|多品牌统一分析架构]] 的统一数据层。
2. 其"单 DuckDB + DuckLake 即满足 <10GB 级"的定位与本项目 36 品牌明细量级高度契合，但 926×/105× 是**厂商自测极值**，落地前必须 POC 复现，不能当作承诺值。
3. 可作为 Iceberg/Hudi 的**并exist 备选**而非立即替换——保留 Iceberg v3 兼容 deletion vectors，意味着迁移成本可控、可灰度切换。
