# 零售经营语义层建设指南：门店/会员/商品/订单指标统一四层法

> **一句话摘要**：面向零售经营的语义层四层建设法（Aloudata 2026 + Eggknite 指标契约实践）——对象语义层（先回答"什么是有效订单/会员如何唯一/统计到 SKU 还是 SPU"）→ 共享维度层（时间/商品/渠道/门店/会员五大公共坐标）→ 指标语义层（基础/派生/复合三层可组合指标，替代数百个静态指标）→ 消费服务层（BI/报表/Agent 消费同一套语义）。多品牌场景下"销售额只维护一套基础逻辑，用维度和业务限定动态组合"。
> **来源**：Aloudata 零售语义层建设指南 + Eggknite Metric Contracts（2026）
> **置信度**：媒体估算（语义层厂商方法论指南 + 技术博客，无审计数据）
> **brand_specific**：false（行业通用方法论，双链 concept/practice，不链品牌）
> **最后更新**：2026-09-03

## 核心要点

1. **建语义层前先统一"对象语义"**：必须回答——什么是一笔有效订单？会员如何唯一识别？商品统计到 SPU、款式还是 SKU？线上订单归属哪个渠道/区域/门店？退款/取消/赠品/跨店履约如何处理？**关系不统一，指标层再完整也撑不起跨域分析**。
2. **优先统一高复用公共维度，不是所有维度**：时间（财年/周定义/同环比周期）、商品（分类层级/新品规则）、渠道（线下/官网/电商/门店类型归属）、地域门店、会员（唯一会员/标签生效周期）。"华东区销售额"和"华东区会员数"必须引用同一个地域维度。
3. **指标三分层（可组合指标）**：基础指标（支付金额/订单数/件数/会员数/库存数量等最小可复用事实）→ 派生指标（+时间周期/业务限定/维度，如"近 30 天购买会员数"）→ 复合指标（客单价/转化率/复购率/动销率/**售罄率**/库存周转天数）。"销售额"只维护一套基础逻辑，靠维度与业务限定组合，不重复建口径近似指标。
4. **消费服务层必须多端同义**：经营驾驶舱、固定 BI 报表、自助分析、Excel/WPS、**Data Agent 消费同一套指标语义**——"销售额"不再属于某张报表，而成为可被多消费端调用的语义资产。
5. **指标契约（Metric Contract）是落地机制**：一指标一 YAML（owner/definition/grain/freshness SLA/change policy/consumers），放 git、CI 校验、改动需 owner 审批；给 AI 分析 Agent 只发语义层 API 凭证、撤销裸表权限；90 天查询日志可回放"这个数怎么来的"。5 人团队 10 个指标约 2 周可落地。

## 详细内容

### 四层语义层架构（零售版）

| 层 | 统一对象 | 关键问题 |
|----|---------|---------|
| ① 对象语义层 | 有效订单/唯一会员/统计粒度/渠道归属 | 退款取消赠品跨店履约怎么算？SPU vs 款式 vs SKU？ |
| ② 共享维度层 | 时间/商品/渠道/地域门店/会员 | 财年起止/周定义/新品规则/门店状态/标签生效周期 |
| ③ 指标语义层 | 基础→派生→复合 三层指标 | 指标可组合、口径单一来源 |
| ④ 消费服务层 | BI/报表/自助/Excel/Data Agent | 多端消费同一语义资产，不各自重写逻辑 |

### 指标三分层示例（可组合指标）

| 类型 | 定义 | 示例 |
|------|------|------|
| 基础指标 | 最小可复用经营事实 | 支付金额、退款金额、订单数、销售件数、会员数、库存数量 |
| 派生指标 | 基础 + 时间周期/业务限定/维度 | 近 30 天购买会员数、本月直营门店销售额、会员订单销售额 |
| 复合指标 | 多指标计算 | 客单价、转化率、复购率、动销率、**售罄率**、库存周转天数 |

> "真正该统一的是**计算原子和组合规则**，而不是强行把所有业务场景压缩成一张静态指标清单。"

### 指标契约最小规范（Eggknite，AI Agent 前置）

```yaml
# metric contract（放 git + CI 校验 + owner 审批）
metric: active_customers
owner: fpa-team@example.com
definition:
  measure: COUNT(DISTINCT account_id)
  filter: contract_end_date >= current_date
grain: day
freshness_sla: 24h
change_policy: breaking_change_requires_owner_approval
consumers: [board_deck, churn_model, ai_analyst]
```

- 五个工件：指标注册表（每指标一 YAML）/ 契约 JSON Schema / 代码评审门（CODEOWNERS）/ **Agent 白名单（只给语义层 API 凭证）** / 查询日志（90 天）。
- 核心理念：**"能拒绝的 Agent 比需要审计的 Agent 更可信"**——模型回答"该指标不在注册表"不是失败，而是护栏在工作。

## 结论

1. **语义层是 [[multi_brand_unified_analytics|多品牌统一分析架构]] 指标计算层 2026 的落地形态**：多品牌（太平鸟/卡宾/东尚 35 品牌场景）最大的痛是"同一指标各品牌各算一遍"——"销售额"按品牌配置驱动只维护一套基础逻辑，用品牌/渠道/时间维度动态组合，正是本方法的核心主张，与 [[brand_config_driven_system|品牌配置驱动系统]] 天然互补（配置管字段映射，语义层管指标口径）。
2. **对象语义层的五个问题直接命中本项目痛点**：卡宾渠道结构复杂（特许/代销/线上/OEM 四形态并存，见 [[cabbeen_brand_analytics_2026]]）、多品牌字段命名各异——"什么是有效订单/统计到 SPU 还是 SKU/线上订单归属"必须先于指标层回答，否则 [[2026-08-26_多品牌零售数据中台与全域用户治理实践2026|OneID]] 之后仍会出现"两个销售额"。
3. **指标契约 = ChatBI/Agent 化（[[2026-08-06_AgenticBI与ChatBI零售落地实测]]）的前置护栏**：先注册 10-15 个高管指标并给 Agent 发"只读语义层凭证"，比先建对话层再补治理安全一个量级——呼应 2026-08 已有"对话层权限继承"结论。
4. **对 kb_benchmarks 的启示**：售罄率/周转/复购等阈值若以"契约 + 时间窗 + 口径声明"形式登记（如 90 天复购 vs 年度复购），跨 source 的"数值矛盾"大半可消解为"口径未对齐"——语义层能降低未来矛盾检测的假阳性率。
