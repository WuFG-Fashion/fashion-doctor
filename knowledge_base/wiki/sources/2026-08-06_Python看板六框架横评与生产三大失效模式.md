# Python 看板六框架横评与生产三大失效模式（2026）

> **一句话摘要**：2026 年 Python 看板生态扩到六框架（Streamlit/Dash/Gradio/Reflex/Panel/NiceGUI），默认仍是 Streamlit（1–3 天出货，1.55 为 4 月稳定版、每两周发版）；但三条生产红线必须提前知道——**模块级全局变量跨会话泄漏**是头号生产 bug、**`st.dataframe` 超 5 万行崩溃**、**面向客户的多租户分析自建要 4–8 周而嵌入只要 1–5 天**。

> **来源**：UseDataBrain 2026 Python Dashboard Guide + Streamlit vs Dash 2026 + Streamlit 官网 + dev.to 三框架实战
> **最后更新**：2026-08-06

## 核心要点

1. **六框架交付周期**：Gradio 1–2 天 ≈ Streamlit 1–3 天 < NiceGUI 1 周 < Dash 1–2 周 ≈ Panel 1–2 周 < Reflex 2–4 周
2. **版本基线**：**Streamlit 1.55 为 2026-04 当前稳定版**，Snowflake 主导下**每两周发一版**，硬性最低 Python 3.10；推荐 Python 3.13 + pandas 3.x + Plotly 6.x
3. **表格阈值**：`st.dataframe`（Arrow + glide 渲染）**约 1 万行良好、超 5 万行崩溃**；Dash 原生 `dash-table` 同量级；**Dash AG Grid 可扛 10 万行以上**带排序/过滤/透视/分组
4. **多用户红线**：Streamlit 模块级全局变量（文件顶部的 `df = pd.read_csv(...)`）**在同进程所有会话间共享**，一个用户的筛选会泄漏进另一个用户的视图——这是上多用户生产流量时选 Dash 的头号理由
5. **不该自建的边界**：面向客户的多租户 SaaS 分析，自建要 4–8 周做 auth+RBAC+多租户+导出+定时邮件层，嵌入 Databrain/Metabase/Cube 只要 1–5 天

## 详细内容

### 六框架适用矩阵

| 框架 | 交付 | 最适合 | 崩溃点 |
|------|------|-------|-------|
| Streamlit | 1–3 天 | 内部数据科学看板、原型 | 多用户状态、细粒度交互、渲染超 5 万点 |
| Dash | 1–2 周 | 企业级多页应用、精细回调、大表 | 学习曲线陡；超约 30 个组件后回调链失控 |
| Gradio | 1–2 天 | AI/LLM 看板、模型演示、聊天 UI | 不像模型演示的形状（无真网格布局、图表稀疏） |
| Reflex | 2–4 周 | 纯 Python 全栈 + React 级前端 | 生态小；SSR + 状态模型有尖角 |
| Panel (HoloViz) | 1–2 周 | 科学计算看板（HoloViews/Bokeh/Datashader） | 社区小、可查答案少 |
| NiceGUI | 1 周 | 既要看板又要表单的内部工具 | 小众 |

**决策规则**：默认 Streamlit → 撞上 rerun 模型 / 需要多页企业应用 / 需要 AG Grid 扛十万行时换 Dash → 看板本质是 LLM 演示时用 Gradio → 客户侧多租户直接买嵌入式。

### 生产三大失效模式

| # | 失效模式 | 现象 | 处置 |
|---|---------|------|------|
| 1 | **模块级全局状态泄漏** | 文件顶部加载的 DataFrame 被所有会话共享，改动互串 | 所有可变状态进 `st.session_state`；只读数据用 `@st.cache_data`；多用户生产考虑 Dash（回调无状态 + `dcc.Store` 按浏览器会话作用域） |
| 2 | **大表渲染崩溃** | 超 5 万行 `st.dataframe` 浏览器吃不消 | 服务端分页/聚合后再渲染；重心是大表则用 Dash + AG Grid（`streamlit-aggrid` 是第三方且维护不够活跃） |
| 3 | **玩具数据幻觉** | 用 3 行数据演示，上 5 万行生产数据就卡 | **一开始就用 5 万行真实规模 CSV 做开发基线**，让缓存与渲染行为匹配现实 |

### 部署与扩展

- Streamlit：GitHub → Community Cloud 免费层一键 Deploy（仅公开应用）；HF Spaces 同样一键；生产用 Docker，**注意 `streamlit run` 不是多进程——只能横向多实例扩展**；企业级私有走 Snowflake（无限私有应用）
- Dash：gunicorn + Render/Fly.io/自建 K8s，或付费 Dash Enterprise（托管 + SSO + RBAC + 版本控制）。首次部署摩擦略大，但因为就是普通 Flask 应用，生产扩展更干净

### 动态刷新机制对照

| 框架 | 机制 |
|------|------|
| Streamlit | `st.session_state` + `@st.cache_data`/`@st.cache_resource`；第三方 `st.autorefresh()` 或 `st.empty()` + 轮询（适合低频实时）；默认无原生 WebSocket |
| Dash | 原生 `dcc.Interval` 定时轮询；可接 Flask-SocketIO/自定义 API 做 WebSocket 推送；`dash.long_callback` 支持异步后台任务 |

### 什么时候两个都不该选

AI/LLM 聊天看板 → Gradio；需 React 级前端行为的纯 Python 全栈 → Reflex；客户侧多租户 SaaS 分析 → 嵌入式平台；静态周报 PDF → Quarto 或 Jupyter 管道（实时看板框架是杀鸡用牛刀）。

### Streamlit → Dash 迁移剧本（机械平移）

触发条件：全局状态冲突已在生产咬人 / 需要 AG Grid 扛 5 万行以上 / 需要"此筛选只更新这三张图"的细粒度控制 / 需要回调层强制按用户 RBAC。

组件映射：`st.selectbox`→`dcc.Dropdown`、`st.slider`→`dcc.Slider`、`st.date_input`→`dcc.DatePickerRange`、`st.metric`→样式化 `html.Div`、`st.plotly_chart`→`dcc.Graph`；渲染逻辑包进 `@callback`，每筛选一个 `Input`、每图/KPI 一个 `Output`。

### 对本项目的直接映射

- 本项目是 Streamlit 多 Tab 多品牌看板，**失效模式 #1 是当前最高风险**：若多店长/多品牌负责人同时访问，模块级加载的品牌数据可能互串——需逐项审查数据加载是否都在 `@st.cache_data` 之内、可变筛选是否都进了 `st.session_state`
- 明细 Tab（SKU 级动销明细）容易越过 5 万行阈值，应在服务端先聚合或分页，而非直接 `st.dataframe(df)`
- Plotly 6.x 破坏性变更需在升级前确认现有图表代码
- pandas 3.0 的 CoW 收益在看板侧是"白拿"，与 [[arrow_zero_copy_interop_2026]] 的零拷贝链路叠加
