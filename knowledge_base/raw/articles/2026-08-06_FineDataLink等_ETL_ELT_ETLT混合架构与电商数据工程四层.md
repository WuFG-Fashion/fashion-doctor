## 一、2026 年三种模式对照

| 模式 | 典型应用场景 | 技术平台举例 | 优势 | 劣势 |
|------|------------|------------|------|------|
| ETL | 金融、制造、规范化 BI | Informatica、DataStage、FDL | 数据质量高、流程规范 | 性能瓶颈、扩展性差 |
| ELT | 互联网、**零售**、湖仓 | Snowflake、BigQuery、FDL | 扩展性强、实时能力好 | 数据治理难度较大 |
| 混合 ETLT | 传统 + 新兴业务混合 | FDL、Databricks | 灵活、兼容性强 | 运维复杂、选型难 |

ETL 强调流程控制，ELT 突出平台能力。云原生、低代码、可视化开发成为主流诉求。

## 二、什么时候必须选 ETL（5 类场景）

1. 中小制造/**零售企业，日数据百万条以内**：ERP/MES/进销存/门店 POS 体量小，无分布式数仓，仅需 T+1 财务报表与库存统计，ETL 部署简单、运维成本低
2. 转换逻辑高度复杂且规则固定：多表关联、多层计算、跨系统主数据合并、编码映射（国产数据库与 Oracle 字段兼容），固定逻辑放中间层统一维护，避免重复写 SQL
3. 源系统算力薄弱、禁止大批量查询压库：老旧业务系统支持分批次、分时段限流抽取 + 定时增量
4. **主数据 MDM 统一分发**：组织/客户/物料主数据标准化清洗后统一分发到下游多业务系统，必须通过 ETL 保证唯一主键与统一编码，确保全集团口径一致
5. 合规要求数据不能以原始形态落库（需在传输中脱敏）

## 三、什么时候必须选 ELT（4 类场景）

1. 海量行为数据：埋点/时序/订单日志/IoT 每日千万至亿条、PB 级存储
2. 实时大屏、智能推荐、实时风控：ELT 快速加载原始数据 + Flink 实时流处理建模，缩短数据产出延迟
3. 数据科学与 AI 建模探索：完整留存全量原始数据，分析师自由筛选加工，不受前置转换规则限制
4. 已建成云原生/分布式湖仓：Snowflake、MaxCompute、TDSQL-C、Doris、Hudi 等 MPP 引擎算力充足，适合把转换逻辑卸载到仓内

## 四、2026 最优主流方案：ETL+ELT 混合批流一体

**90% 中大型企业不再二选一，采用单平台双模式切换**：

- 核心交易、主数据、敏感报表 → 走 ETL 前置清洗
- 海量日志、用户行为、实时分析、大数据建模 → 走 ELT 快速入库
- 全场景增量同步统一依赖 **CDC 变更捕获**，实现毫秒级增量，打通离线与实时数据链路

### 2026 工具强制必备功能清单（缺失即淘汰，七大模块）

基础集成能力 / 实时 CDC 能力 / 转换加工能力 / 调度运维 / 数据治理 / 信创安全 / 扩展服务

### FDL 零售全渠道案例

某连锁零售过去门店/商城/电商平台/会员运营数据分散。引入 FDL 后**快速对接 30+ 数据源**，全量+增量同步，配合 Kafka 实时入仓；低代码配置搭建数据中台，历史与实时数据全部入仓，支撑营销/供应链/财务分析。

ELT 新应用趋势：

| 场景类型 | 典型行业 | 新趋势 |

| AI/BI 一体化分析 | 制造、医疗 | ELT 与机器学习无缝衔接，低代码开发 |
| 数据资产治理 | 政府、能源 | 元数据管理、血缘追踪、质量自动检测 |

## 五、电商数据工程四层栈（Mercuryminds）

| 层 | 内容 | 关键点 |
|----|------|-------|
| Layer 1 数据源 | 订单/客户/商品/客服工单/广告平台（Meta/Google/TikTok） | **供应商主数据最常被忽略**：产品成本、交货周期、规格直接喂给定价决策、毛利报表与目录准确性。只做客户与订单集中化而把供应商数据留在邮箱里 = 只解决一半问题 |
| Layer 2 摄取与 ELT | Fivetran、Airbyte 等托管连接器 | 先落原始数据再转换，转换规则错了还能重跑；连接器维护是"无趣但难"的活，源平台改 API 时可能静默失败三周无人察觉。**ETL/ELT 工具市场 2026 年规模超 100 亿美元** |
| Layer 3 数仓 | Snowflake / BigQuery / Databricks / Redshift（2026 四大主流） | 单一事实来源在此实现；LTV 从真实订单历史计算，而非被三个工具各算一遍 |
| Layer 4 建模 | **dbt 成为主导** | 把版本控制、测试、文档等软件工程纪律引入过去无人敢改的临时 SQL 脚本 |

### 数仓选型的实际判据

| 平台 | 典型强项 | 电商考量 |
|------|---------|---------|
| Snowflake | 预建集成生态强，存算分离干净 | 被 reverse ETL 与 BI 工具广泛支持，中型电商常见默认选择 |
| BigQuery | 与 Google 广告/分析生态紧密 | 若 Google Ads / GA 是营销核心则天然契合 |
| Databricks | 结构化 + 非结构化（图像/文本）+ ML | 计划做计算机视觉目录处理或较重 ML 建模时值得考虑 |
| Redshift | 与 AWS 生态深度集成 | 履约或基础设施已在 AWS 上时自然契合 |

**关键判断**：没有一个是孤立意义上的错误选择；更重要的是哪个与现有技术栈（云厂商、广告平台、ML 工具）最自然集成，而不是逐条比功能。**换仓后期可行但代价高昂**，值得第一次就选对。

## 六、Databricks + dbt + Delta Lake 的企业 ELT 实现（Lucent）

- **Databricks（Spark）= 计算引擎**：算力与存储独立扩缩；Delta Live Tables 支持声明式管道 + 内建数据质量约束——转换要么通过质检要么管道停止告警，而不是静默产出错误数字
- **dbt = 转换层**：所有业务逻辑以 SQL/Python 模型形式存在，Git 版本控制 + 文档化血缘。业务分析师问"这个收入数字从哪来"，答案是 dbt 血缘图而不是找资深工程师口头传承。**三层结构**：staging（与源表一对一，最小转换）→ intermediate（为特定用例做连接与整形）→ mart（面向消费者的最终表，供 BI 与报表）
- **Delta Lake = 存储层**：云对象存储上的 ACID 事务、schema 强制、时间旅行。时间旅行对电商数据团队尤其有价值——可查询任意历史时点的订单数据，调试指标差异时可精确复现两个状态
- **Unity Catalog = 全栈治理**：集中访问控制、从原始摄取到 BI 看板的全链路血缘、PII 分类，是让 ELT 栈可审计合规的关键

### 决策框架

| 你的处境 | 推荐模式 | 原因 |
|---------|---------|------|
| 多渠道且数据量增长 | ELT（Databricks + dbt） | schema 变更、历史重算、实时需求 |
| PII 或敏感数据不能原始存储 | ETL + 传输中脱敏 | 合规要求先转换再存储 |
| 装入固定 schema 的遗留系统 | ETL | 目标系统无法处理原始或中间数据 |
| ML/AI 与分析并行 | ELT（Databricks） | 模型训练与报表同源，无重复 |
| 实时或准实时报表 | ELT（Delta Live Tables） | 流式摄取 + Delta Lake 增量模型 |
| 小体量、稳定 schema、简单用例 | ETL 或简单脚本 | 完整 ELT 栈是过度投入 |
| 从遗留 ETL 迁移 | ELT（并行运行） | 验证输出一致后逐源切换 |

### ⚠️ 混合陷阱（Hybrid Trap）

**最昂贵的环境是 ETL 与 ELT 管道都写入同一报表层且无明确归属边界**——业务逻辑存在于两个地方，产出略有差异的数字，没人确定哪个才对。若同时运行两种模式，必须保持严格隔离：不同源域、不同目标 schema、清晰归属。

迁移不必一刀切：许多企业让遗留 ETL 继续喂旧 BI，同时并行搭建新 ELT。重点是**从今天起每条新管道都是 ELT**，遗留 ETL 在替换模型验证后系统性退役。
