# 知识库 v2 架构方案（讨论稿 · 尚未执行）

> 日期：2026-09-11 ｜ 状态：**讨论稿，未动任何文件** ｜ 触发：老板发现 Home→MOC 导航层停在 8-06/8-07、L3 空壳，提出结构 + 内容质量 + 过时机制三方面重构诉求

## 0. 一句话诊断

问题不是"采得不够多"，而是**三种寿命完全不同的东西被塞进了同一套按学科分的目录里**，而且**导航层是人手写的**——手写的东西必然腐烂。

现状三个硬伤（本次已实证）：

| 硬伤 | 证据 | 后果 |
|---|---|---|
| **原料层入口分裂** | KB 根 `raw/articles/` **101 篇** ＋ `wiki/raw/articles/` 783 篇；现状同名交集 = 0，但 git 历史里曾有 **753 个同名**（审核报告的"595 重复"来自历史视角）→ 定性：**旧入口残余 + 新入口，非内容重复**（详见 §13.1） | 入口分裂、维护两遍；合并是收拢残余 |
| **导航层已死** | `Home.md` → MOC×8 → L3 子页；MOC 自 08-09 手写快照后再无主人，页内写死"最近更新：2026-08-06/07"；MOC 指向的 L3 子页只剩 2 个 0KB 空壳 | 入口通向死链 + 假新鲜度（今天就把你误导了） |
| **结构自己没人管** | `wiki/_archive/` 是空目录；CLAUDE.md 内部自相矛盾（架构概览说 L2/L3 已归档退役，第六章说"旧 L2/L3 目录保留作为只读历史"）；4 个根目录 md 处于无主状态 | 结构层腐烂无人发现，RAG 会捡到陈旧垃圾 |

**根因一条**：视图层（Home / MOC / index）是手写 Markdown，不是脚本生成物。内容会腐烂慢，**视图腐烂最快且最容易骗人**。

## 1. 三个需要先纠正的前提（诚实纠偏）

### 1.1 "到期自动作废删除" —— 方向对，机制危险

两个错误隐含假设：

- **时间不是失效判据，衰减速度才是**。2019 年的会员分层方法论可能今天仍有效；昨天的价格档位已经废了。按"入库日期 + 固定天数"删，会把常青方法论杀掉、把易腐数据留着。
- **过期 ≠ 无价值**。过期的门店数不是垃圾，它是**历史时序点**（8 月的 573 店 vs 今天的门店数 = 扩张速度）。直接删等于销毁趋势数据。

→ 改为：**按信息类型分档 TTL + 到期软化（降权→退检索）而非删除**，物理删除必须人批。

### 1.2 "为双链而双链" —— 你现在这套规则里就装着制造它的机器

CLAUDE.md 白纸黑字：

- 5.1 必须包含「**至少一条 `[[双链]]`**」
- 5.2 禁止「**创建没有 `[[双链]]` 的孤岛页面**」

这两条是**硬门槛**。页面为了过关，只能连一条跟推理无关的链——伪链就是这么被逼出来的。MOC 层本身也是"图谱去孤岛工程"的产物，现在变成了死层。

→ 改为：**信息链强制（承载推理）+ 关联自由（无则不罚）+ 可达性由脚本校验**。

### 1.3 "结构要保持更新" ≠ 所有层都要人肉维护

正确的分工是：**视图层由脚本生成、内容判断由人/模型写、规则只能人改**。要求"每一层都保持更新"，结果就是每一层都没人管。今天的 MOC 就是证据。

## 2. 目标态结构：按「谁产生 + 寿命 + 权限」分区（不是按学科）

设计原理：**学科分类（L0-L7 / concepts-entities）会把三种寿命的东西混在一格**——今天的门店数（易腐）、品牌战略（慢变）、零售方法论（常青）放在同一层，就没法设统一的过期规则。所以分区轴必须换成"产生者 + 寿命 + 权限"。

```
knowledge_base/
├── 00_inbox/              临时收集（你随手丢，AI 只读）        TTL 14 天
├── 10_web/                网络采集原文（机器写）                 TTL 按 volatility
│   └── 2026/09/
├── 20_personal/           个人知识沉淀（你写，AI 默认只读+授权代笔）★非公司、非品牌
│   ├── 01_提炼判断与预期/   ← 你自己提炼的知识判断、行业预判、未来预期（非既成事实，你的高价值个人资产）
│   └── 02_感性言论/        ← 观点、随想、行业直觉（**只读素材**：存档备查，不参与合成、不影响判断、不进 RAG）
├── 30_wiki/               编译层（机器写，六类型，现有 wiki/ 保留）
│   ├── sources/ entities/ concepts/ comparisons/ practices/ playbooks/
├── brand_wall/            品牌墙（共享品牌库，增长无上限，机器+人维护，慢变）
│   ├── cabbeen/           卡宾（独立，东尚重点读取 ★）
│   ├── peacebird/         太平鸟（独立，东尚重点读取 ★）
│   └── <其它品牌>/        将来只增不减，公司按需从此读取（现有 focus_brands 35 个在此）
├── 40_companies/          公司域（每公司一目录，RAG 硬隔离边界）
│   └── dongshang/         东尚（运营主体，重点读取 brand_wall 的 cabbeen+peacebird）
│       ├── 01_制度/            门店制度、考核、薪酬、审批权限
│       ├── 02_人员架构/        组织图、岗位职责、汇报线
│       ├── 03_业务梳理/        业务流程、商品链路、渠道结构
│       ├── 04_语义层/          指标契约 YAML（口径/字段映射/血缘）★
│       ├── 05_证据/            东尚会议纪要、报表快照、洞察（带 TTL）
│       └── 06_培训课件/        ← 现有 human/培训课件（34 篇，非 322）迁入，属东尚体系内
├── 50_legacy/             历史归档（旧 L2/L3、失效页；只读，永不物理删）
└── 90_meta/               规则/索引/健康/日志（CLAUDE.md、_health、__index__、log.md）
```

> **关键关系澄清（2026-09-11 老板拍板）**：
> - `20_personal/` = 你**个人**的知识沉淀（提炼判断/预期 + 感性言论），既不是公司资料、也不是品牌资料，默认不进任何公司 RAG。
> - `human/培训课件` 是**东尚公司体系内**的培训课件，归 `40_companies/dongshang/06_培训课件/`，而非个人域。
> - `卡宾 / 太平鸟` 依然**独立在品牌墙 `brand_wall/`**，是东尚的「重点读取」对象；品牌墙继续维护、只增不减，将来其它公司也从这里读取各自需要的品牌。品牌墙是跨公司的**共享品牌参考层**（公共可读），但各公司域（制度/架构/业务/证据）彼此隔离。

### ★ 最大的复用杠杆：`40_companies/<公司>/04_语义层/`

这份"指标契约"（指标名 / 口径 / 字段映射 / 血缘 / 生效期）**就是东尚数据分析系统正在做的语义层改造**（老板纠偏：**不钉死版本**——真源按「当前主版本」指针跟随，当前=V3，未来 V4/V5 只切指针、不改规则）。同一份真源，两处消费：

- 东尚系统主版本后端（当前 V3）：SQL 计算与看板口径
- KB / RAG：检索时作为"口径解释器"注入 prompt（用户问"售罄率"时带上你的定义，而不是行业泛义）

**不做两份**——这是本方案性价比最高的一条。

## 3. 重要性怎么分层（你指定要先想清楚的部分）

关键认知：**"重要性"和"寿命"是两个正交维度，混着设计必然出错**。所以拆成三个独立维度：

| 维度 | 回答什么问题 | 用途 | 取值 |
|---|---|---|---|
| **A 权威性** | 这条信息多可信、多能依赖 | RAG 检索排序权重、冲突时以谁为准 | Tier0 规则契约 / Tier1 判断合成 / Tier2 事实 / Tier3 原料 / Tier4 视图 |
| **B 衰减速度** | 多久会被现实推翻 | 过期策略、TTL | 常青 / 慢变 / 快变 / 易腐 |
| **C 权限域** | 谁能看 | 公司隔离、隐私红线 | 公共 / 公司域 / 个人域 |

### 分层表

| Tier | 内容 | 谁写 | 衰减 | 权限 | RAG 权重 | 可否删除 |
|---|---|---|---|---|---|---|
| **T0 规则/契约** | CLAUDE.md、指标契约、公司制度 | **只能人写**，机器只读 | 版本驱动（不看时间） | 公司域/公共 | 最高（口径唯一真源） | 只能人删 |
| **T1 判断合成** | comparisons、结论块、playbooks、SOP | 人 + 模型（需人复核） | 慢变 | 公共/公司 | 高 | 人批后归档 |
| **T2 事实** | sources 摘要、公司业务梳理、人员架构 | 模型写，人抽检 | 快变 | 公司域 | 中 | TTL 到期软化 |
| **T3 原料** | 10_web 原文、00_inbox、公司会议纪要 | 机器/你随手写 | 易腐 | 公司域/个人 | 低且过期即退 | TTL 到期软化 |
| **T4 视图** | 公司业务主体看板（订货会前/周会前/竞品异动）、Home、index、图谱 | **脚本生成，人不手写** | 可再生 | 按公司域 | 不参与检索 | **按需生成（慢）·生成后不日维护** |

**三条使用规则**：

1. **T4 不算知识**——视图是可再生派生物，禁止手工维护、禁止参与 RAG 召回。视图按「公司业务主体」生成（如东尚订货会看板、卡宾周会看板），生成慢但**生成后长期有效、不要求每日维护**，只在业务主体变更或触发事件时重建。这一条直接消灭"MOC 死掉"这类问题：视图不该被人当成内容，更不是每日负担。
2. **冲突时高 Tier 压低压**：T1 结论与 T3 原文冲突 → 更新 T1；T0 契约与任何页冲突 → 契约赢（并且那条页要标矛盾）。
3. **T3 是消耗品，T2 是资产入口**：判断一个页该怎么对待，先问"它是原料还是事实"。

## 4. 过时设计（核心机制）

### 4.1 三个新字段（在现有 frontmatter 上扩展）

```yaml
volatility: evergreen | slow | fast | perishable   # 衰减档（决定默认 TTL）
as_of: 2026-08-31          # 信息观察时点 ← 关键：不是写入日期
expires_at: 2026-11-29     # = as_of + 档位天数，可由人覆写
status: active | stale | expired | retired          # 状态机
reviewed_at: 2026-11-29    # 最近一次人工/自动复核
```

**为什么必须区分 `as_of` 和 `created`**：8 月 30 日抓到的"某品牌 2025 财年门店数"，写入日是 8-30，但信息时点是更早的。用写入日算过期，会一律算早；用 `as_of` 才算得准。

### 4.2 分档标准（草案，需你一起定值）

判定口诀（给你用的行业口径）：**这条信息"下一次被现实推翻"大概要多久？**

| 信息类型 | 档 | 默认 TTL | 到期动作 | 例外 |
|---|---|---|---|---|
| 价格 / 促销 / 折扣 / 库存状态 | 易腐 perishable | 7–30 天 | 退检索 + 转时序点 | 历史价格序列保留 |
| 门店数 / 渠道 / 联名活动 / 人事变动 / 新店开业 | 快变 fast | 90 天 | 退检索 + 待复核 | 财报口径的门店数按财报期 |
| 财报 / 季度经营数据 / 大盘指标 | 慢变 slow | 下一期披露日 | `superseded_by` 指向新期 | 保留全部历史期（时序） |
| 方法论 / 框架 / 课件 / 行业研究 | 常青 evergreen | 180 天**复核**（不硬过期） | 复核：仍有效则续期 | 有明确时效的行业数据除外 |
| 制度 / 组织架构 / 口径契约 | 版本驱动 | **不看时间** | 变动即出新版本 | 旧版进轮换保留 |
| 感性言论 / 个人洞察（20_personal） | 常青 | 不过期 | 仅标"观点演进"；**只读素材，不进任何公司 RAG** | 与旧观点冲突时并列而非覆盖 |

### 4.3 到期后做什么——三档动作，不删

```
active ──到期──▶ stale ──无复核──▶ expired ──人批──▶ retired(50_legacy)
   │              │                    │
   │              │                    └─ 保留 as_of，作为历史时序点参与趋势对比
   │              └─ 降权（RAG 仍可召回，排序下调）
   └─ 退检索（默认不召回，显式检索仍可见）
```

**硬规则**：自动化**只有权标记与建议，无权删除**。软化满 30 天无异议，才进"建议删除"清单交你批。原件永不物理删除（git 留底）。

### 4.4 谁来跑

新脚本 `tools/kb_ttl.py`（挂在现有 `kb_updater.py` 之后）：

1. 扫全库 frontmatter → 算出到期清单
2. 写 `_health/YYYY-MM-DD_ttl_report.md`
3. A/B/C/S 轮启动时若发现"本域有 expired 页" → **先处置再采集**（把过时风险压在日常里，不攒批）

## 5. 双链重设计（反"为双链而双链"）

### 废除
- ❌ 5.1「至少一条 `[[双链]]`」硬门槛
- ❌ 5.2「禁止孤岛页面」
- ❌ "零孤岛"作为质量门

### 替换为三条**可脚本校验**的规则

| 规则 | 内容 | 校验方式 |
|---|---|---|
| **R1 信息链完整** | 每页必须有「上游来源 → 本页判断 → 下游应用」；下游若暂时没有，必须显式写 `(open: 待谁用)` | 脚本检查区块存在 + 至少 1 上游 1 下游 |
| **R2 可达性** | 任一页从 `index.md` 出发 ≤3 跳可达 | 脚本跑图算法（不达标由**脚本在 index 补链接**，而不是逼页面造假链） |
| **R3 链接有效** | 所有 `[[目标]]` 必须真实存在 | 脚本校验（MOC 那种指向空气的链直接报错） |

### 关键新增：把"拓展"机制化
每页必须有 **`## 前沿`（frontier）** 区块：这一步还缺什么信息、下一步该查什么、哪个假设待验证。

- 这是你说的"知识库应该一直去拓展"的落地形式——**扩张靠 `前沿` 驱动，不靠加链**
- 自动化下一轮可以直接把上一轮的 `前沿` 当采集输入（形成闭环，而不是无脑按品牌名搜）

### 链接分两类字段
- `information_chain`（强制，承载推理，参与 RAG 多跳）
- `related`（自由，可有可无，无则不罚）

## 6. 公司域 × RAG 检索设计

### 6.1 每公司一个 `company.yaml`
```yaml
company: 东尚
aliases: [dongshang, 东尚时尚, 黄石东尚]
scope: company              # company | public_only
read_brands: [cabbeen, peacebird]   # ★ 重点读取品牌墙中的这两个品牌（其余按需追加）
db: ${PEACEBIRD_DB} ${CABBEEN_DB}
semantic_layer: 40_companies/dongshang/04_语义层/
allowed_layers: [T0, T1, T2]   # 该公司域参与检索的层级
```

### 6.2 检索流程（原理层，六步）
1. query → 解析出公司实体（无则默认公共层 `30_wiki/`，不含任何公司域）
2. **硬过滤 scope**：
   - 本公司域 `40_companies/<c>/`（制度/架构/业务/证据/课件，彼此隔离）
   - 共享参考层 `brand_wall/`（公共可读，所有公司可引用其中的品牌页）
   - 公共编译层 `30_wiki/`
3. 品牌归并：命中 `brand_wall/<brand>/` 的页，仅当该品牌 ∈ 本公司 `read_brands` 或 query 显式点名才纳入（东尚默认只带 cabbeen+peacebird，避免把 35 个品牌全卷进来）
4. 域内 BM25 / 向量召回
5. 取 `04_语义层/` 的指标契约做**口径解释器**注入（把"售罄率"钉到你的定义）
6. 按 Tier 权重排序输出；`status: expired` 的页不参与

### 6.3 隔离红线
- 个人域（`20_personal/`）**不进任何公司 RAG**（决策④ ✅，默认不入）。`01_提炼判断与预期` 与 `02_感性言论` 均为私密个人资产：前者是你高价值个人判断、后者是只读素材，二者都不参与公司回答的召回；如需回看个人沉淀，走独立的个人检索通道，不作为公司 RAG 答案的一部分。
- 品牌墙是**跨公司共享参考层**（公共），但各公司只读取自己 `read_brands` 内的品牌；**A 公司的制度/架构/业务信息不得出现在 B 公司的回答里**
- 跨公司只允许命中公共层 `30_wiki/` 与品牌墙；公司专属证据不外溢
- 落地顺序：先 `dongshang` + `brand_wall/{cabbeen,peacebird}`（已有 DB 与 brand_configs），验证隔离正确再扩其它品牌/公司

| 病 | 症状 | 根因 | 处方 |

| **A 源病** | 抓来一堆自宣/营销软文，"读完等于没读" | 采集按"品牌名+最新"检索，没有信源分级与配额 | 来源分级（财报/官方 > 第三方 > 自宣/媒体）+ 每轮低信源**配额上限**；5 关审核升级为**打分卡**（数据密度/可行动性/新颖度/来源等级），低于阈值不建页只归档 |

### 13.2 采纳：frontmatter 数据契约（对象模型定死，先于一切目录动作）

每页互不混淆的 11 个字段（T0-T4 管"知识角色"，confidence 管"数据可信度"，**两者永不合并**）：

```yaml
type: source | entity | concept | comparison | practice | playbook
layer: T0 | T1 | T2 | T3 | T4            # 知识角色（规则/判断/事实/原料/视图）
scope: public | brand | company | personal
company: dongshang                        # scope=company 时必填
volatility: evergreen | slow | fast | perishable | versioned
as_of: 2026-09-11                         # 信息观察时点
review_due_at: 2027-03-10                 # 常青页复核日（不自动过期）
expires_at: 2026-11-29                    # 易腐/快变/慢变页到期日
status: active | stale | expired | retired   # retired 仅人批后产生
superseded_by: "[[新页]]"                  # 版本替代（制度/契约/财报）
retrieval: eligible | explicit_only | never  # 检索准入（个人域=never，T4=explicit_only）
```

### 13.3 采纳：TTL 三轨拆分（不把三种寿命塞进一个 status）

| 衰减档 | 用什么字段 | 到期行为 |
|---|---|---|
| 易腐 / 快变 / 慢变 | `expires_at` | 到期 → stale → expired（退检索），物理删除仍须人批 |
| 常青 | `review_due_at` | 到期只触发**复核**，不自动变过期；复核通过则续期 |
| 版本驱动（制度/契约/口径/财报） | `superseded_by` | 新版落盘即替代旧版，旧版转时序点保留 |

- **财报"下期披露日"未知**：默认给保守值（180 天）+ `as_of` 备注预计披露窗口，人可覆写
- `retired` 状态**只能人工批准后产生**，自动化无权写入

### 13.4 采纳：双链只校验四件事（废除形式化"上下游各一条"）

1. 上游来源存在；2. 下游链接有效**或**显式标 `(open: 待谁用)`；3. 无断链（指向空气即报错）；4. 从生成的总索引出发 ≤3 跳可达。
- `## 待办 / 待验证` 与 `## 前沿` **合并为一个区块**（名字用 `## 前沿`），不允许同时维护两套
- **机器真源唯一**：正文 `## 信息链` 是唯一真源，frontmatter 不再重复 `information_chain` 字段（删）

### 13.5 采纳：RAG 隔离在建索引前完成（不是检索后过滤）

- 每公司**独立索引 / 独立 collection**；个人域（`retrieval: never`）**根本不进公司索引**
- 每条目写入 `scope/company/retrieval` 元数据后才允许自动化写公司域
- 先过**隔离测试**（A 公司 query 不得召回 B 公司域任何条目）再放开写入
- **明确边界**：当前仓库单主人私有，所谓"公司隔离"= **RAG 检索隔离，不是文件访问控制**（见 §14 六点之④）

### 13.6 采纳：T4 视图"不进向量召回，但允许显式注入"

订货会看板不被普通问答召回（`retrieval: explicit_only`），但生成经营分析时可被明确作为上下文附加——否则视图生成后没人用得上。

### 13.7 采纳：语义层唯一真源 = 东尚系统「当前主版本」（版本指针机制，不钉死 V3）

## 10. 三个反驳（按"先反驳再执行"铁律）

1. **物理搬迁的风险被低估**：6 条自动化（A1/A2/A3/B/C/S）的路径都写死在 prompt 与脚本里，搬迁期索引与 RAG 会短暂失效，且要同步改 6 份规范。
   → **替代方案（我更倾向）**：先做**逻辑分层**——用 frontmatter `layer:` + `domain:` 字段表达新结构，脚本照字段生成视图与检索 scope，**物理目录暂不动**。收益接近，风险小一个数量级。物理搬迁可以永远不做。
2. **TTL 有误杀风险**：万一某条"过期"信息其实是关键历史证据，软化虽不删但会被检索忽略。
   → 缓解：`expired` 仍可被显式检索命中；到期报告强制人过一眼；分档值先保守（宁可长不可短）。
3. **公司域与公共层必然重复**：同一份财报既是公司证据，也是行业情报。
   → 原则：**原文单点存储（放公司域），公共层只放合成结论**。代价是公共层结论页要跨域引用，链接校验要支持跨域路径。
