# 分布式知识库架构可行性评估
**方案**：WorkBuddy（Windows 采集） + Karpathy LLM Wiki + fnOS Hermes（NAS 编译） + Obsidian（载体）
**评估日期**：2026-08-06 | **评估人**：WorkBuddy

---

## 0. 结论先行

**总体可行，且高度贴合你现有资产——但必须做 3 处硬修正，否则会踩坑。**

- ✅ 核心架构逻辑成立：采集/编译/载体三层分工合理，Obsidian 作为纯 md 底座的"数据自持"判断完全正确。
- ✅ 关键依赖全部真实存在：Hermes 是 fnOS 应用商店上架的原生 fpk 智能体；fnOS 支持 Docker 私有大模型；ZeroNews/FN Connect 穿透可用。
- ⚠️ **硬修正 1（最关键）**：用 **Git 仓库做跨设备同步底座**，不要用 NFS/SMB 挂隧道实时挂载。你现有的 Round C 流程已经在用 `git push`，这是比 NFS-over-WAN 健壮得多的方案，原方案把它换掉是倒退。
- ⚠️ **硬修正 2**：Hermes 不是"装好就完事"。自主 7×24 编译会静默累积错误，必须加 **lint/CI 闸门 + 人工矛盾审阅环**。
- ⚠️ **硬修正 3**：商业合规与暴露面——fnOS 个人免费、商业需授权；Hermes 微信网关 + 隧道是真实攻击面，必须只读隔离 + 强鉴权。

## 2. 原方案架构（简要还原）

```
[Windows/WorkBuddy] --采集/清洗--> raw/ --跨网同步--> [fnOS/Hermes] --编译--> wiki/ --> [Obsidian Vault]
                                                  (NFS/SMB over ZeroNews 隧道)        (双链/图谱/多端查阅)
```

分工：Windows 负责外网抓取与业务系统对接；NAS 常驻编译；Obsidian 做静态底座。两端共用同一 Vault 形成"共享大脑"。

## 3. 方案做对的地方（应保留）

1. **三层分工合理**：外网/调度放 Windows（不占 NAS 外网带宽），长时增量编译放 NAS（7×24 常驻），与硬件资产匹配。
2. **Obsidian 作为终点正确**：全量 md、不绑定任何 AI 程序，Hermes/WorkBuddy 未来更替时知识库永久可用——这正是服装门店长期沉淀运营手册/货品知识的核心诉求。
3. **目录权限隔离思路正确**（你提的 `raw/wiki/human/AGENTS.md` 四分法）：这与你现有 `CLAUDE.md` 的"raw 只读、wiki 单一 AI 维护"硬规则**完全一致**，是整套架构不出乱子的命门。
4. **版本回滚意识正确**：只是实现方式应选 Git（见修正 1），而非额外再搭一套快照。

## 4. 必须修正的 6 个隐患

### 4.1 同步层：用 Git 替代 NFS-over-WAN（最关键）
- **原方案**：Windows 通过 ZeroNews 隧道把 NAS 的 `/raw` 挂载为远程盘，WorkBuddy 往里写。
- **问题**：NFS/SMB 跨公网隧道做**持续双向写入**是文件同步最脆弱的形态——半写入文件、文件锁冲突、时序错乱会让 Hermes 读到残缺 raw 而生成错误词条。你自己在"原方案隐患 1"里也点到了这点，却用"隧道挂载"去解，治标不治本。
- **修正**：让 **Git 仓库成为同步底座**（你现有流程已经在做 `git add && commit && push`）。
  - WorkBuddy 提交 `raw/` → push；
  - Hermes `git pull` 取 raw → 编译 → 提交 `wiki/` → push；
  - WorkBuddy 需要时 `git pull` 取回 wiki 实现"共享大脑"。
  - Git 天然提供：原子提交、冲突检测、**完整历史与一键回滚**（=你想要的版本备份，免费送）。
  - ZeroNews/FN Connect 仍保留，但**只用于 Hermes 控制台与微信问答网关**，绝不用于文件同步。

### 4.2 Hermes 不是"装好就完事"——必须加 lint 闸门
- 自主 7×24 编译会静默漂移：命名不规范、双链断链、重复建页。
- 修正：Hermes 每次批量更新 **wiki/ 前**，先跑你现有的 `_kb_lint_all.py` + 矛盾检测脚本（CLAUDE.md §3.4/§3.5），**不通过则禁止提交**。把 Schema 约束写进代码，而非只写进 AGENTS.md 散文。

### 4.3 矛盾检测必须 human-in-the-loop
- 实测：本轮 Round C 的矛盾检测曾把"Pandas 3.0 文本列内存降 50%"误判为与基准 `memory_saving_pct=0.87` 冲突——其实一个是 pandas 内部增益、一个是 Polars-vs-Pandas 口径，不矛盾。**自主 Agent 没有这个判断力**，会错误地"修正"或静默忽略。
- 修正：矛盾/异常 → **标红进每日摘要 → 人工裁定**，绝不自动改写历史词条。

### 4.4 Obsidian 双链映射标准化
- 你现有 wiki 用 `[[page.md]]` 格式；Obsidian 原生偏好 `[[page]]`（无后缀）才能图谱视图干净渲染。`cross_refs:` 自定义 frontmatter Obsidian 会忽略，无碍。
- 修正：统一为 `[[page]]`（去 `.md`），让 Obsidian 图谱/反向链接零摩擦。

### 4.5 商业合规
- fnOS 个人免费、商业需授权；Hermes 为社区 fpk（非飞牛官方商业支持）。服装连锁门店部署前**确认 fnOS 商业授权与 Hermes 支持边界**。

### 4.6 暴露面安全
- Hermes 微信/飞书网关 + ZeroNews 隧道 = NAS 局部暴露公网。门店员工问答入口是真实攻击面。
- 修正：问答网关**只读**访问 wiki/、强鉴权、IP 白名单；raw/ 与 human/ 绝不让网关触碰。

## 6. 落地路线建议（渐进，不一步到位）

1. **Phase 0（现在就有）**：你现有 `D:\Fashion Doctor\fashion-doctor` 已是完整 Karpathy LLM-Wiki（CLAUDE.md + raw/ + wiki/ + L2/L3 + 矛盾检测 + git push）。单机跑通。
2. **Phase 1**：在 fnOS 装 Hermes + 配置模型供应商（Kimi/MiniMax 延迟低、中文好）；建 Git 仓库（GitHub 或 NAS 本地 git）作为同步底座。
3. **Phase 2**：把 `CLAUDE.md` + 现有 Python 编译/lint 脚本整体迁移到 Hermes 可调用；先让 Hermes **只读**跑一遍编译，对比 Windows 端产出，验证一致性。
4. **Phase 3**：开启 Hermes 写入 + lint 闸门 + 每日矛盾摘要人工审阅；Windows 端改为只产出 raw/ 并 push。
5. **Phase 4**：Obsidian 打开 Vault，确认双链/图谱；按需开放微信只读问答网关（带鉴权）。

## 7. 与你现有 KB 的映射（重要）

你现有 Fashion Doctor 知识库**已经实现了原方案约 80% 的逻辑**，区别只在"单机 vs 分布式"：

| 原方案角色 | 你现有实现 |
|---|---|
| Karpathy LLM Wiki Schema | `knowledge_base/CLAUDE.md`（§3.2 采集/§3.4 矛盾/§3.5 织网） |
| raw/ 只读原始层 | `knowledge_base/raw/articles/` |
| wiki/ 编译层 | `knowledge_base/wiki/{sources,concepts,practices}/` + `L2_*/L3_*/` |
| 矛盾检测 | `kb_benchmarks.json` + `_kb_contradiction_check.py` |
| 自动织网 | `_roundC_0806_update.py`（双链 + 回链） |
| 同步/版本 | `git add && commit && push`（已验证可用） |

**也就是说，分布式改造的本质 = 把"编译层"从 Windows 移到 fnOS/Hermes，并引入 Git 作跨设备同步。** 你不需要从零搭建，只需迁移与验证。
